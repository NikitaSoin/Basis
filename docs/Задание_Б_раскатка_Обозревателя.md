# Задание агенту Б — раскатать «Обозреватель» на платформу

## Контекст
Прототип — один статичный HTML-файл (`observer-sidebar-v2.html`) с 9
разделами (сайдбар), построенный на выдуманных/иллюстративных данных.
Задача — перенести **структуру, поведение и JS-логику**, подключив реальные
данные с бэкенда вместо статичных JS-массивов. Выполнять **после** того как
поручение А (дизайн-система) подключено и проверено — тогда этот раздел
будет визуально согласован с остальным сайтом автоматически.

## Product logic — что переносим
9 разделов, сгруппированных в 3 зоны сайдбара:
- **Данные:** Лента новостей, Экономическая статистика
- **Рынок:** Карта рынка (drill-down treemap), Календарь событий (список +
  сетка месяца), Отчёты
- **Разбор:** Макроэкономика, Геополитика, Институциональная среда,
  ИИ-обзор и анализ (+ отдельная страница «История отчётов»)

## Backend/data model — что нужно на бэкенде

Перечень сущностей, для которых сейчас в прототипе — статичные JS-данные,
а на проде должны быть реальные API-эндпоинты:

| Раздел | Нужна сущность | Пример полей |
|---|---|---|
| Экономическая статистика | `MacroIndicator` (временной ряд) | date, value, indicator_key |
| Карта рынка | тикер + % изменения + вес (капа) | ticker, sector, change_pct, market_cap |
| Календарь событий | `CalendarEvent` | date, type (macro/dividend/earnings/board/ipo), title, ticker |
| Отчёты | `EarningsReport` | ticker, period, revenue_pct, ebitda_pct, profit_pct, positives[], risks[], conclusion |
| Макроэкономика / Геополитика / Институты | `AnalysisNote` | topic, mode (overview/assessment), content, source |
| ИИ-обзор и анализ | `Report` | topic, depth, created_at, content, model |

**Важно:** при генерации `EarningsReport` — числовые поля (revenue_pct и
т.д.) должны храниться как структурированные значения со знаком **на
этапе генерации**, не как текст для последующего парсинга. При тестовом
переносе была поймана реальная проблема: попытка вытащить проценты из
готового текстового предложения регулярным выражением дала неверный знак
в нескольких случаях (например дефис в диапазоне "13-15%" читался как
минус). Хранить структурированно с самого начала — единственный надёжный
способ избежать этого класса ошибок.

## Frontend/UI logic
- Взять разметку и JS из прототипа как основу.
- Заменить статичные JS-массивы (`SERIES_DATA`, `MAP_SECTORS`,
  `CALENDAR_EVENTS`, `REPORTS_COMPACT` и т.д.) на `fetch()`-вызовы
  к соответствующим эндпоинтам.
- Вся остальная логика (treemap-алгоритм, календарь-сетка, dropdown,
  фильтры, drill-down) не завязана на источник данных — переносится как
  есть, меняется только ОТКУДА берутся данные, не КАК они рисуются.

## Риски
1. **Illustративные данные.** Часть контента в прототипе — заглушки
   (институциональная среда, геополитика по регионам, часть отчётов) — для
   них ещё не существует пайплайна генерации на бэкенде. Раскатывать
   структуру можно сразу, наполнение — по мере готовности соответствующих
   генераторов (например через отдельных Claude-субагентов, как уже
   принято в проекте для market-analyst/governance-analyst).
2. **Объём.** Не переносить все 9 разделов одним PR/коммитом — по одному
   разделу за раз, с проверкой на реальных данных перед переходом к
   следующему.

## Как проверить
На каждый перенесённый раздел — сверить, что реальные данные с бэкенда
корректно проходят через ту же визуальную логику (цвет по направлению,
фильтры, drill-down), что и в прототипе на иллюстративных данных.
